# Week 5 - C5 Pandas Analysis

## Competency Claim: C5 - Data Analysis with Pandas

**What it means**: Using pandas to answer a real question about a dataset. Filtering rows, grouping, aggregating, handling missing values. Choosing the right pandas operation for what you are trying to find out, and interpreting the result.

## How I Did That 
In `a5_pandas_analysis.ipynb`, I used pandas as the core tool to turn raw Riot API JSON into analysis-ready tables and answer practical data questions. First, I fetched Bronze IV ranked solo player records from the League endpoint, loaded them into a DataFrame, and inspected structure with `head()`, `shape`, and null checks to verify column quality. Next, I used pandas operations to profile the dataset (for example, counting repeated IDs with `value_counts()` and duplicate checks), then cleaned it by deduplicating on unique keys (`puuid` for player-level data and `match_id` for match-level data). I also grouped and summarized columns to test assumptions and interpret what each field represented for the analysis goal.

I then built a second pandas DataFrame from `match_ids_by_puuid.json` by flattening nested JSON into one row per `(puuid, match_id)` pair. From there, I quantified repeated match IDs, identified overlaps, and created a deduplicated match table to prevent inflated frequencies in later support pick-rate calculations. This shows competency C5 because I selected pandas operations intentionally for each step (inspection, filtering, grouping, aggregation, deduplication, and validation), and used the outputs to make evidence-based decisions about data quality and analysis reliability.

I've detailed my process step-by-step in `a5_pandas_analysis.ipynb`. It's currently a work in progress, as I had to repeat this process for 3 different API endpoints, but the endpoints that I did manage to fetch data from should be sufficient enough for a proof-of-concept. 

## My Learnings
1. Using HCI principles while editing a script- specifically the one that describes how visual feedback should be provided to users whenever they complete an action. I ran into this a lot while I was first fetching data from the API. The first time I ran my script, it failed after 2 minutes (without completing its API request loop) due to an HTTP 429 error. However, because I didn't have visual confirmation of where I left off, I had no idea which pages had been requested from the API already and which hadn't, resulting in around multiple repeated rows. In future scripts for API requests, I made to sure to include flags that tracked how many API requests had already been made and stored locally Additionally, I made sure to add a line that resumes API requests where it got left off in the case of an interruption, making the code more user friendly for myself. 

2. I didn't realize that the amount of data I'll eventually need to analyze really compounds over time. In the first API I used, 1 request = 1 page, and 1 page had 205 rows of player data on it (including the PUUIDs). I initially wanted to fetch Match ID information for each of those 51,400 something PUUIDs, but due to request limits, I capped it at 500 PUUIDs so that my data analysis could still be statistically significant. For each PUUID, I fetched 10 Match IDs. And eventually for each of those around 5000 Match IDs, I'll have to fetch champion data. While I had to cap my API requests for this assignment, this made me realize that I'll have to be really intentional about when and how often I make API requests for the final MP1 deliverable.
